**AI model for real-time motion generation. No animations. No keyframes. No mocap. No hard work.**

MotionCraft is a motion AI — it learns how to move by trying, failing, and improving. Instead of pre-recorded animations, movement is generated live in response to player input and the environment's state. The model runs locally on your machine — no cloud, no latency. We train the model. It handles the rest.

This is an **early MVP**. It demonstrates one thing: a skeleton character generating locomotion in Unreal Engine 5, entirely from the model. No animation assets, no blend trees, just the network output driving the joints. A proof of concept that the technology works inside a real-time game engine.

## Getting started

Everything runs on one machine: the model is a small Python process, Unreal talks to it over a
local socket. No GPU required.

### Prerequisites

| | |
|---|---|
| Unreal Engine | 5.8 |
| C++ environment | Visual Studio or JetBrains Rider |
| Python | 3.13 |
| GPU | Not needed: the model runs on the CPU in a few milliseconds per step |
| OS | Windows 11 *(only tested platform)* |

### Set up the model (once)

From the project root:

```bash
python -m venv .venv
.venv\Scripts\python -m pip install -r model/requirements.txt
```

### Run the demo

1. Start the model and leave it running:

   ```bash
   .venv\Scripts\python model/server.py
   ```

   It prints `Motion model ready on 127.0.0.1:41911` and waits for Unreal.

2. Open `MotionPrototyping.uproject` in UE 5.8 and let it rebuild the C++ module.

3. Press **Play**. The character holds a standing pose for two seconds while the joints settle,
   then the model takes over and it starts walking.

4. Use **WASD** to steer and the mouse to look around. The input changes the direction the model
   is asked to walk in; every movement you see is generated by the model and simulated by the
   physics engine.

Stop and press Play as often as you like; the model server keeps serving until you close it
with Ctrl+C.

### When it does not work

| Symptom | Fix |
|---|---|
| `Motion model not reachable` on screen | The server is not running. Start it (step 1), then press Play again. |
| `Cannot listen on 127.0.0.1:41911` from the server | Another server is already running (reuse it), or the port is taken. Pick another with `--port`, and set the same address in `ModelAddress` on the character's *Parity Animation Component*, or launch Unreal with `-MotionModel=127.0.0.1:<port>`. |
| The character moves in slow motion | The game waits for the model every physics step, so a busy CPU slows the game down rather than making the motion wrong. Close other heavy programs. |

## How it works

```
 Unreal Engine (30 Hz, 8 physics substeps)             model/server.py
 ───────────────────────────────────────────          ─────────────────────────────
 read the 15 simulated bodies of the avatar
 build the 228-value observation         ── obs ──▶   high-level controller: picks a
                                                      motion latent every 5 steps
                                         ◀─ 28 ───    low-level controller: joint
 actions → joint targets → Chaos drives    actions    actions from obs + latent
 simulate one step
```

The loop is lockstep: Unreal sends one observation and waits for the answer before the physics
step continues, so the model never falls behind or out of sync. The character has no animation
assets at all; the skeletal mesh is a ragdoll whose joint motors are driven by the model.

| Path | What it is |
|---|---|
| `model/policy.py` | The two policy networks and how a step is computed |
| `model/server.py` | The socket server Unreal connects to |
| `model/weights/policy.pt` | The trained weights |
| `Source/MotionPrototyping/PhysicalAnimation.*` | The loop on the Unreal side: hold, observe, act |
| `Source/MotionPrototyping/ParityObservation.*` | Builds the observation exactly as the model was trained on it |
| `Source/MotionPrototyping/ParityFKRetarget.*` | Turns the model's joint targets into joint drive targets on the UE skeleton |
| `Source/MotionPrototyping/ParityTcpLink.*` | The socket |

## Current limitations

- Forward and turning motion only; there is no stop command yet, so the last heading stands.
- The model cannot see terrain. In the village it will happily walk off the edge of the starting
  terrace, so steer it with WASD.
- The model is trained on a specific skeleton. Custom characters require retraining.

## Why we're building this

3D games demand animation — motion capture, dedicated animators, and hard work. For solo developers and small teams, that cost often means staying in 2D or shipping something that feels wrong. MotionCraft is built on the idea that character movement should be generated, not hand-authored.

The long-term goal: characters that handle complex terrain, react to their environment, and move naturally — all from a model, with no animation pipeline. A solo developer ships a 3D game without learning animation. An indie team iterates on movement without rebuilding state machines. A studio prototypes locomotion in hours instead of weeks. A content creator records a game teaser with believable characters and no hand-crafted animations.

This MVP is the first step.
